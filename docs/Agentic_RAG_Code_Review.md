# Agentic RAG — Code Review

Reviewed: full repo (`backend/` FastAPI + LangGraph RAG pipeline, `frontend/` React app). Findings are ranked by severity within each area. Line numbers refer to the files as uploaded. I independently re-verified the top three findings against the source before including them below.

## Top priority — fix these first

1. **Chunk overlap doesn't work at all** (`backend/ai/services/chunking_service.py:51-56`). The code computes the trailing overlap correctly, then immediately throws it away with `current_doc = [s]` on the next line. Every chunk boundary loses context, which quietly degrades every retrieval in the app. This has no test coverage, so it's been silently broken.

2. **Every chat request blocks the whole server for other users** (`backend/ai/services/embedding_service.py:31-63`, called from `backend/ai/tools/vector_search.py` and `backend/ai/services/retrieval_service.py`). `SentenceTransformer.encode()` and `CrossEncoder.predict()` are synchronous, CPU-bound calls made directly inside `async def` functions with no `asyncio.to_thread`/executor. Since FastAPI runs on a single event loop per worker, one user's embedding+rerank call stalls every other concurrent request on that worker — including unrelated `/health` calls. Also, `vector_search.py:28` checks `hasattr(embedding_service, "get_embedding")` to try to use an async path, but that method doesn't exist on the service (only `generate_embedding`/`generate_batch_embeddings` do) — the check is dead code and the blocking path always runs. Fix: wrap the embedding/rerank calls in `asyncio.to_thread(...)`.

3. **The vector/full-text-search indexes were never actually created** (`backend/alembic/versions/f06fbea045e1_add_vector_and_fts_indexes.py:21-32`). Both `upgrade()` and `downgrade()` are empty `pass` statements — the migration's filename promises HNSW/GIN indexes but creates nothing. Any environment provisioned purely via `alembic upgrade head` has no indexes on `document_chunks`, so the hybrid search query in `retrieval_service.py`/`vector_search.py` degrades to full scans as the corpus grows, and latency will climb linearly with document count. (Also worth noting: the baseline migration only has `ALTER COLUMN`/one `CREATE INDEX` — no `CREATE TABLE` — so it looks like the real schema in dev was created via `Base.metadata.create_all` rather than Alembic, which means Alembic can't be trusted as the source of truth for schema right now.)

4. **The self-correction/reflection step is skipped on the most failure-prone path** (`backend/ai/agents/graph.py:134-144`, `:57-68`). Whenever local vector search returns zero chunks, `web_search_node` overwrites `intent` to `"WEB_SEARCH"` — and `route_after_answer` exempts `WEB_SEARCH` from the groundedness/reflection check. So the exact scenario most likely to produce a hallucinated answer (empty knowledge base → web fallback) is the one case that never gets self-checked.

## Backend — AI / RAG pipeline (`backend/ai/`)

- **Chunk size isn't actually a hard cap** (`chunking_service.py:19-36`): if a single unsplit unit (e.g. a dense table row with no nearby separator) exceeds `chunk_size`, it becomes one oversized chunk with no further splitting. Combined with #1 above, chunk sizes can vary a lot more than the `600`/`120` config implies.
- **Prompt injection surface via retrieved content** (`backend/ai/prompts/answer_prompt.py:1-13`, `backend/ai/agents/answer.py:9-14, 47-52`): document text and web-search results are spliced straight into the system prompt with no "treat this as untrusted data" framing. A crafted PDF or web page can attempt to override instructions. Low blast radius today (no downstream tool execution), but worth hardening, especially for the web-search path where content is fully external.
- **No size limit on chat message / image payloads** (`backend/app/schemas/chat.py:6-9`): `ChatRequest.message` and `image_data` (base64 image) have no `max_length`, unlike the upload endpoint which does enforce a size cap. A large payload can inflate LLM token cost, blow the context window, or slow down/timeout the request — with no application-level guard before it reaches the LLM call.
- **Two independently-drifting retrieval implementations** (`vector_search.py` used by chat, `retrieval_service.py` used by `/search`): different RRF handling, different rank functions, different page-number fallback logic, and `retrieval_service.py` has no `asyncio.to_thread` wrapping at all around its embedding call. These will silently diverge in result quality between `/chat` and `/search`.
- **`.doc` uploads are advertised as supported but always fail** (`backend/ai/services/parser_service.py:65-68`): legacy binary `.doc` is routed to `python-docx`, which only reads OOXML `.docx`. Real `.doc` files always raise and the document is marked `status="failed"` — not a crash, but a misleading "supported" extension.
- **Minor**: hardcoded `model_used="gemini-3.5-flash"` in telemetry logging (`backend/app/routes/chat.py:168, 277`) regardless of the actually configured model — logs will lie if the model config changes.
- Verified working correctly: the reflection retry loop does cap at `max_retries=2` (confirmed by tracing `answer_node`'s retry counter — no infinite loop risk there), and `web_search_tool` correctly offloads its blocking DuckDuckGo call via `asyncio.to_thread` with no SSRF surface (no arbitrary-URL parameter).

## Backend — API / infrastructure (`backend/app/`)

- **Raw exception text returned to clients** (`backend/app/routes/chat.py:118-129, 295-302`, `backend/app/routes/search.py:61-70`): `detail=str(e)` is sent straight into HTTP responses and the SSE error stream. Any unexpected internal error (bad DB URL, malformed pgvector cast, an SDK error containing internal detail) leaks implementation details to the client. Should be logged server-side and replaced with a generic client-facing message.
- **No pagination on list endpoints** (`backend/app/routes/session.py:33-45, 69-92`): `GET /sessions` and `GET /sessions/{id}/messages` return everything in one query with no limit/offset. A long-lived user with thousands of sessions or a long conversation will get an unbounded response and a full-range read on every page load.
- **`get_chat_session()` silently returns any session when `user_id` is omitted** (`backend/app/database/crud.py:111-129`): `user_id` is `Optional`, and when falsy the WHERE clause drops the ownership filter. Every current call site does pass `user_id` (confirmed — no live IDOR today, and `tests/test_security.py` covers this), but the function is a footgun: a future call site that forgets the parameter reintroduces an IDOR with no type error or warning. Worth making `user_id` required.
- **In-memory, unbounded, per-worker cache** (`backend/app/auth/dependencies.py:118`): `_last_sync_time` dict grows forever with one entry per user ever seen, and isn't shared across worker processes — a slow memory leak plus inconsistent "sync every 5 minutes" behavior depending on which worker handles a given request.
- **`Document`/`DocumentChunk` timestamps are naive, unlike every other model** (`backend/app/models/document.py:37-39`, `backend/app/models/document_chunks.py:41-43`): they use bare `datetime.utcnow()` (deprecated) and non-timezone-aware columns, while `User`/`ChatSession`/`Message`/`AgentLog` all use timezone-aware timestamps. Minor now, but a landmine if these ever get compared/sorted together.
- **Missing `SUPABASE_JWT_SECRET` startup check** (`backend/app/config/settings.py`): if left empty, every request silently falls back to a remote Supabase network round-trip for auth verification instead of fast local JWT verification — this shows up only as unexplained latency, with no warning at startup.
- Verified working correctly: parameterized SQL throughout `retrieval_service.py` (no injection risk), CORS defaults to an explicit allow-list (not `*`), JWT verification pins `HS256` and checks expiry, file upload enforces a size limit and offloads storage calls via `asyncio.to_thread`, and cascade delete rules are consistent across the ORM models. IDOR protection on `/sessions`, `/search`, `/chat`, and `/upload` is correctly enforced and has explicit test coverage.

## Frontend (`frontend/src/`)

- **Streamed tokens can land in the wrong chat session** (`frontend/src/context/ChatContext.jsx:152-256`): the streaming callbacks update "the last message in the array" with no check that the active session is still the one the stream belongs to, and the underlying `fetch()` in `chatApi.js:30` has no `AbortController` to cancel an in-flight stream. If a user switches sessions (e.g. deletes the active one) while a response is still streaming, tokens can get appended into the wrong conversation.
- **Auth tokens stored in `localStorage`** (`frontend/src/api/supabaseClient.js:10`): `createClient` is called without an `auth.storage` override, so Supabase defaults to persisting access/refresh tokens in `localStorage`, which is readable by any injected script (XSS in the app itself or in a dependency) — unlike an httpOnly cookie. Worth deciding deliberately rather than by default.
- **Upload size limit is UI text only, not enforced** (`frontend/src/components/Upload/UploadButton.jsx:17-22, 129`): the button says "Max 15MB" but nothing in the component or `useUpload.js` actually checks file size before uploading — it's cosmetic. Real enforcement needs to happen (and does, per the backend review) server-side, but the client should also check to avoid a bad UX (a multi-GB file hanging the tab).
- **Unbounded base64 images kept in memory for the whole session** (`frontend/src/components/Chat/ChatInput.jsx:22-36`, `ChatContext.jsx:168`): no size check before `readAsDataURL`, and the resulting data URI is retained in the messages array indefinitely. Several large image attachments in one long session will bloat memory and can degrade/crash the tab on low-end devices.
- **`localStorage.clear()` on logout** (`frontend/src/context/AuthContext.jsx:54`): wipes all same-origin localStorage data, not just the auth token — any unrelated app data (drafts, flags) gets silently deleted too.
- **Deferred session-clear can race a fast re-login** (`frontend/src/context/ChatContext.jsx:47-53`): clearing state on logout happens inside a `setTimeout(..., 0)` rather than synchronously; a quick logout→login can let the deferred clear fire after the new user's data has already loaded, briefly wiping the UI.
- **No memoization during token streaming** (`frontend/src/components/Chat/MessageList.jsx`/`MessageItem.jsx`): every streamed token triggers a full re-render of the whole message list (no `React.memo`, no virtualization), which will cause visible jank on long chat histories.
- Minor: `SourceBadge.jsx` uses array-index React keys instead of stable IDs; `ChatContext.jsx` has an apparently dead/duplicate `fetchSessions` function alongside near-identical inline logic; client-side file-extension checks are trivially spoofable (fine for UX, just not a real safeguard — the backend needs to be the actual gate, and it is).
- Verified working correctly: no XSS in message rendering (`MessageItem.jsx` renders plain text, no `dangerouslySetInnerHTML`), `ProtectedRoute.jsx` correctly waits for `loading` before evaluating auth (no flash of protected content), `streamParser.js`'s SSE buffering is correct (proper partial-line handling, no unbounded growth), and the axios interceptor re-derives the token per-request instead of caching a stale one.

## Suggested fix order

Given the impact, I'd tackle these in order: (1) the chunking overlap bug and (2) the blocking embedding/rerank calls, since both directly hurt answer quality and latency on every single request; (3) actually creating the vector/FTS indexes, since retrieval will get slower as documents accumulate; (4) exempting the web-search fallback from reflection; then the exception-leakage and pagination issues on the backend, and the streaming-session-race and localStorage-token-storage items on the frontend.
