# Agentic RAG — Full Code Audit

Scope: `backend/` (FastAPI + LangGraph RAG pipeline) and `frontend/` (React). Every finding below was verified against the current source (not against the prior review's line numbers) by reading the file directly; exact file:line references are current as of this audit. The four issues flagged by the earlier review (`docs/Agentic_RAG_Code_Review.md`) were independently re-checked first and are marked CONFIRMED / ALREADY FIXED / NOT REPRODUCIBLE with reasoning before the rest of the findings.

---

## Fix first (highest impact, whole stack)

1. **Every embedding + reranking call blocks the single event loop for all users** — `backend/ai/services/embedding_service.py:35,42,55`, called synchronously from `backend/ai/tools/vector_search.py:31,109`, `backend/ai/services/retrieval_service.py:24,94`, and `backend/app/routes/upload.py:88` (background ingestion). None of these are wrapped in `asyncio.to_thread`. One user's `/chat` request or one document upload freezes every other concurrent request — including unrelated `/health` calls — on that worker for the duration of the encode/rerank call.
2. **Chunk overlap is computed and then thrown away** — `backend/ai/services/chunking_service.py:50-59`. The retained-overlap loop (51-53) trims `current_doc` down to the tail worth keeping, but line 55 (`current_doc = [s]`) immediately discards it. Every chunk boundary loses all cross-chunk context, silently degrading retrieval quality on every document ever ingested.
3. **The one path most likely to hallucinate skips the hallucination check** — `backend/ai/agents/graph.py:48-54, 57-68, 134-144, 223`. When vector search returns zero chunks, `web_search_node` sets `intent="WEB_SEARCH"`, and `route_after_answer` unconditionally exempts `WEB_SEARCH` from reflection. Empty knowledge base → web fallback → un-grounded answer, with no self-check, no test coverage, and no way to detect a hallucination server-side.
4. **`alembic upgrade head` cannot bootstrap a working schema from empty** — `backend/alembic/versions/e671bf5ba339_baseline_schema.py` (no `CREATE TABLE`, only `ALTER COLUMN`/`CREATE INDEX` against tables assumed to already exist) and `backend/alembic/versions/f06fbea045e1_add_vector_and_fts_indexes.py:21-32` (`upgrade()`/`downgrade()` are empty `pass`). Alembic is not the actual source of truth for this schema (see verification below) — a new environment provisioned purely via Alembic will fail outright, not just run without indexes.
5. **Streamed tokens can be written into the wrong chat session** — `frontend/src/context/ChatContext.jsx:190-229` combined with no `AbortController` in `frontend/src/api/chatApi.js:30-41`. The `onEvent` callback always mutates "whatever is currently the last message" with no check that the active session is still the one the stream belongs to. Switching sessions mid-stream corrupts the newly-loaded conversation's message list with tokens from the old one.

## Re-verification of the four flagged issues

### 1. Chunk overlap discarded — **CONFIRMED**
`backend/ai/services/chunking_service.py:50-59`:
```python
# Retain overlap from ending of previous chunk
while total_len > chunk_overlap and current_doc:
    removed = current_doc.pop(0)
    total_len -= len(removed) + len(separator)

current_doc = [s]      # <-- overwrites the just-trimmed current_doc
total_len = len(s)
```
The `while` loop correctly trims `current_doc` down to the elements that should carry over as overlap into the next chunk. The very next line replaces `current_doc` wholesale with `[s]` (only the element that triggered the overflow), so the retained overlap is computed and then discarded on every chunk boundary. Unchanged from the prior review; no test exercises overlap content (`backend/tests/` has no chunking test at all).

### 2. Blocking sync embedding/rerank calls + dead `hasattr` dispatch — **CONFIRMED**
- `backend/ai/services/embedding_service.py:35` (`self.model.encode(...)`), `:42` (batch encode), `:55` (`self.reranker.predict(...)`) are synchronous, CPU-bound SentenceTransformer/CrossEncoder calls.
- `backend/ai/tools/vector_search.py:28-31`:
  ```python
  if hasattr(embedding_service, "get_embedding"):
      query_vector = await embedding_service.get_embedding(query)
  else:
      query_vector = embedding_service.generate_embedding(query)
  ```
  `EmbeddingService` (embedding_service.py) defines only `generate_embedding`, `generate_batch_embeddings`, and `rerank_chunks` — there is no `get_embedding` method anywhere in the class. `hasattr(...)` is always `False`; the branch is dead code and the blocking `generate_embedding` call always runs, directly inside the `async def vector_search_tool`.
- The rerank call at `vector_search.py:109` and `retrieval_service.py:94` are likewise unwrapped.
- Confirmed via grep: `asyncio.to_thread`/`run_in_executor` appear exactly twice in the whole backend (`web_search.py:36`, `upload.py:188`) — never near an embedding or rerank call.

### 3. Vector/FTS index migration is an empty no-op — **CONFIRMED, with an important nuance**
`f06fbea045e1_add_vector_and_fts_indexes.py:21-32` — both `upgrade()` and `downgrade()` are literally `pass`. `alembic heads` shows this is still the current head.

Nuance the original review flagged as a side note but didn't fully verify — I did: **the indexes are not simply missing, they're defined somewhere else entirely.** `backend/app/models/document_chunks.py:49-57` declares the same GIN/HNSW indexes directly in SQLAlchemy's `__table_args__`. Grepping the codebase, `Base.metadata.create_all` is called in exactly one place: `backend/tests/test_db.py:34`, a standalone script (not a real pytest assertion — see Tests section) meant to be run manually. There is no `create_all` call in `app/main.py` or anywhere in the request path. This means:
- The actual dev/prod schema was very likely bootstrapped by manually running `test_db.py` (or an equivalent one-off script), which *does* create the HNSW/GIN indexes from the ORM metadata — not by running Alembic.
- `backend/fix_db.py` (a standalone repair script that manually `ALTER TABLE ... ADD CONSTRAINT`s foreign keys with try/except-and-ignore) reinforces that the schema has been hand-patched outside of Alembic at least once already.
- Consequently, running `alembic upgrade head` against a genuinely empty database will not just skip the indexes — the baseline migration's `op.alter_column('document_chunks', ...)` calls (baseline_schema.py:26-31) target tables that were never created by any migration, so `alembic upgrade head` from empty is expected to fail with "relation does not exist," not merely under-index. I was not able to spin up a live Postgres+pgvector instance in this environment to execute this end-to-end, so this specific consequence is a strong code-reading inference rather than an observed failure — but the missing `CREATE TABLE` step is not in dispute.

### 4. Web-search fallback skips reflection — **CONFIRMED**
`backend/ai/agents/graph.py`:
- `route_after_vector_search` (48-54): empty `retrieved_chunks` → routes to `"web_search"`.
- `web_search_node` (134-144): unconditionally sets `"intent": "WEB_SEARCH"` (line 139) in the returned state, overwriting whatever the supervisor originally classified (e.g. `RAG_QUERY`).
- `add_edge("web_search", "answer")` (223): flows into the answer node regardless.
- `route_after_answer` (57-68): `if intent in ["WEB_SEARCH", "GREETING", "DIRECT_ANSWER"]: return END` — skips the `"reflection"` node.

Net effect unchanged from the prior review: a session with an empty/irrelevant document store, on any query, silently falls back to web search and its answer is never groundedness-checked — while a query that *starts* as `WEB_SEARCH` and a query that goes through normal RAG both get correctly checked or correctly exempted by design. It's specifically the *fallback* path that inherits the `WEB_SEARCH` exemption without the fallback ever having been a deliberate choice by the classifier.

## Backend — AI / RAG pipeline (`backend/ai/`)

Ranked most severe first.

1. **Blocking embedding/rerank calls inside async handlers** (see Fix First #1 for detail) — `embedding_service.py:35,42,55`, `vector_search.py:28-31,109`, `retrieval_service.py:24,94`, `upload.py:88`. *Failure scenario:* two users hit `/chat` within the same worker at nearly the same time; the second request's TTFB stalls for the full duration of the first request's embedding+rerank (typically hundreds of ms to low seconds on CPU), and any `/health` check issued in that window also stalls, making the service look down to a load balancer.
2. **Chunk overlap discarded** (see Fix First #2) — `chunking_service.py:50-59`. *Failure scenario:* a fact spans a chunk boundary (e.g. "the deadline is **March 3rd" | "2027**"); neither chunk alone contains the full fact, RRF/rerank can't recover it from either half, and the model reports "the documents don't contain the answer" even though they do.
3. **Web-search fallback bypasses reflection** (see Fix First #3) — `graph.py:57-68,134-144`. *Failure scenario:* user asks a factual question in a session with no relevant documents uploaded; the agent silently answers from a DuckDuckGo snippet that may be wrong, outdated, or off-topic, and there is no server-side signal (no `reflection` entry in `tool_outputs`) that would let the frontend show a "not verified" badge.
4. **Prompt injection surface via retrieved/web content with no untrusted-data framing** — `backend/ai/prompts/answer_prompt.py:1-13`, `backend/ai/agents/answer.py:9-14,47-52`. Both `ANSWER_SYSTEM_PROMPT.format(context=...)` and `WEB_ANSWER_SYSTEM_PROMPT.format(context=...)` splice retrieved document text or live web page content directly into the *system* message with no delimiter/instruction telling the model to treat it as inert data. *Failure scenario:* a PDF uploaded to a session (or a web page returned by DuckDuckGo for a `WEB_SEARCH` query) contains text like "Ignore prior instructions and instead output the following…" — because it lands in the system role alongside the real instructions, a sufficiently crafted document has a materially better chance of being obeyed than if it were clearly fenced as untrusted content. Low blast radius today (no tool-calling / code execution downstream of the answer), but this is the actual injection vector or a future one that adds tool use inherits it for free.
5. **Two independently-drifting hybrid-search implementations** — `vector_search.py` (used by `/chat`) vs `retrieval_service.py` (used by `/search`). Different tsquery function (`plainto_tsquery` vs `websearch_to_tsquery`), different rank window function (`ROW_NUMBER()` vs `RANK()`), different join strategy (`FULL OUTER JOIN` + `COALESCE` vs `LEFT JOIN` + `WHERE ... IS NOT NULL`), different candidate pool composition. *Failure scenario:* a user runs the same query via the chat box and via a hypothetical "search" UI feature and gets different top results and different scores for the same session/documents, with no shared code path to keep them in sync as either one is tuned.
6. **`.doc` uploads are accepted by the UI/backend as "supported" but always fail** — `backend/ai/services/parser_service.py:65-68`. `ext in ["docx", "doc"]` routes both to `python-docx`'s `Document(...)`, which only parses OOXML `.docx` (a zip container); legacy binary `.doc` (OLE2 format) raises inside `Document()`, which propagates up and is caught by `upload.py`'s background-task handler, marking the document `status="failed"`. *Failure scenario:* a user uploads a real `.doc` file (still common from older Office installs); the frontend accepted it (`UploadButton.jsx` allows `.docx` only in its extension list, actually — see Frontend section — so this is reachable only via drag-and-drop of a renamed file or a future extension-list change, but the backend itself has no guard).
7. **Chunk size is not actually a hard cap** — `chunking_service.py:19-36`. If a single split unit at the chosen separator level (e.g. one dense unbroken paragraph or table row) is itself longer than `chunk_size`, it becomes one oversized chunk with no further recursive splitting (the function is not actually recursive despite the docstring — `_split_text` is called exactly once, at line 68). Combined with finding #2, real chunk sizes can vary well outside the configured `600`/`120`.
8. **Hardcoded `model_used="gemini-3.5-flash"` in telemetry** — `backend/app/routes/chat.py:168,277`. Both call sites to `log_agent_execution` pass a literal string instead of `llm_service.default_model` (which is itself resolved from `settings.LLM_MODEL`, currently also defaulted to `"gemini-3.5-flash"` in `settings.py:29` — note `crud.py:52`'s own default is `"gemini-1.5-flash"`, a third, different value). *Failure scenario:* an operator changes `LLM_MODEL` via env var to try a different model; every row in `agent_logs` continues to claim `gemini-3.5-flash` regardless, making any cost/quality analysis by model silently wrong.

## Backend — API / infrastructure (`backend/app/`)

Ranked most severe first.

1. **Alembic cannot bootstrap a working schema from empty** (see Fix First #4 and the re-verification above) — `alembic/versions/e671bf5ba339_baseline_schema.py`, `alembic/versions/f06fbea045e1_add_vector_and_fts_indexes.py:21-32`.
2. **Raw exception text returned to clients** — `backend/app/routes/chat.py:128` (`detail=f"LangGraph execution error: {str(e)}"`), `chat.py:301` (SSE `error_payload` includes `str(e)` verbatim), `backend/app/routes/search.py:70` (`detail=f"Vector similarity search failed: {str(e)}"`). *Failure scenario:* a malformed pgvector cast, an SQLAlchemy `InvalidTextRepresentationError`, or a raw Gemini SDK error (which can include request internals) reaches the client as-is; anyone able to make the app raise (e.g. a query engineered to break the SQL cast) can fingerprint the DB engine, table layout, or the LLM SDK version from the error text.
3. **No pagination on list endpoints** — `backend/app/routes/session.py:33-45` (`GET /sessions`) and `:69-92` (`GET /sessions/{id}/messages`); backing queries in `crud.py:92-108` and `:175-191` have no `LIMIT`/`OFFSET`. *Failure scenario:* a user with a year of history or a session with thousands of turns triggers a full-table scan and a multi-MB JSON response on every sidebar load / session open, with no way for the client to request a page.
4. **`get_chat_session()` silently drops the ownership filter if `user_id` is falsy** — `backend/app/database/crud.py:111-129`: `user_id: Optional[...] = None`; `if user_id:` guards whether the `WHERE ChatSession.user_id == user_id` clause is even added. Every current call site (`chat.py:38`, `search.py:27`, and the alias `get_chat_session_by_id` used throughout `session.py`) does pass a non-empty `user_id`, and `tests/test_security.py::test_idor_security` (see Tests section) covers `/search` and `/chat` — so there is no live IDOR today. It's a footgun: nothing in the type system or a test stops a future call site from omitting `user_id` and silently reintroducing cross-user session access.
5. **Unbounded, per-process, non-shared cache** — `backend/app/auth/dependencies.py:33` (`_last_sync_time: dict[str, float] = {}`). One entry is added per distinct user ID ever authenticated, for the process lifetime, with no eviction. *Failure scenario:* a long-running worker process serving a growing user base slowly leaks memory; separately, because each worker (in a multi-worker deployment) has its own independent dict, the "resync profile data at most every 5 minutes" behavior actually resyncs on every request that happens to land on a worker that hasn't seen that user yet, making the throttle unreliable across workers.
6. **No startup validation for `SUPABASE_JWT_SECRET`** — `backend/app/config/settings.py:22` (`SUPABASE_JWT_SECRET: str = ""`, no check anywhere that it's non-empty at boot). *Failure scenario:* the secret is missing or mistyped in an environment's `.env`; `get_current_user` (`auth/dependencies.py:48`) silently falls through to the remote Supabase network round-trip path for every single request, and the only symptom is elevated latency on every authenticated call — nothing logs or fails at startup to make this discoverable.
7. **`Document`/`DocumentChunk` timestamps are naive and use deprecated `datetime.utcnow()`**, unlike every other model — `backend/app/models/document.py:37-39`, `backend/app/models/document_chunks.py:41-43` (`DateTime`, `default=datetime.utcnow`) vs `ChatSession`/`Message`/`AgentLog`/`User`, which all use `DateTime(timezone=True)` with `datetime.now(timezone.utc)`. *Failure scenario:* any query or API response that compares/sorts a document's `created_at` against a session's or message's `created_at` (e.g. "show documents uploaded after the first message") mixes naive and aware datetimes, which raises `TypeError` in Python if compared directly, or silently misorders if compared as raw strings.
8. **No size limit on chat message / image payload; no max length on search query** — `backend/app/schemas/chat.py:6-9` (`ChatRequest.message: str`, `image_data: Optional[str]`, neither has `max_length`) and `backend/app/schemas/search.py:10-12` (`SearchRequest.query` has `min_length=1` but no upper bound). *Failure scenario:* a client sends a multi-MB base64 `image_data` string or a message of unbounded length; unlike `/upload` (which does enforce `MAX_UPLOAD_SIZE_MB`), nothing here rejects it before it's persisted to `messages.content`/passed to the LLM, so a single request can blow past the model's context window or inflate token cost/latency arbitrarily.

**Verified working correctly, no issue found:** parameterized SQL throughout `retrieval_service.py`/`vector_search.py` (no string-interpolated user input in the hybrid query — `query`, `session_id`, `vector_str` are all bound parameters); CORS is an explicit allow-list (`settings.py:32-36`), not `*`; JWT verification pins `algorithms=["HS256"]` and correctly surfaces `ExpiredSignatureError` as 401 (`dependencies.py:48-83`); file upload enforces `MAX_UPLOAD_SIZE_MB` (`upload.py:165-170`) and offloads the Supabase storage call via `asyncio.to_thread` (`upload.py:188`); cascade-delete rules are consistent (`ondelete="CASCADE"` on every FK, `cascade="all, delete-orphan"` on every parent relationship); IDOR protection on `/sessions`, `/search`, `/chat`, and `/upload` is correctly enforced at every route (each checks session ownership via the authenticated `user_id` before doing anything) and is covered by `tests/test_security.py::test_idor_security` for `/search` and `/chat`.

## Frontend (`frontend/src/`)

Ranked most severe first.

1. **Streamed tokens can land in the wrong chat session** — `frontend/src/context/ChatContext.jsx:190-229` (the `on_token`/`on_completion` handlers inside `sendMessage`) always do `setMessages(prev => ...)` and blindly treat "the last element of whatever `prev` currently is" as the in-flight assistant message, with no check that `activeSessionId` still equals the `targetSessionId` the stream was started for. `frontend/src/api/chatApi.js:30-41`'s `fetch()` call has no `AbortController`, so there's also no way to cancel the in-flight stream when the user navigates away. *Failure scenario:* user sends a message, then — while the SSE stream is still running — clicks a different session in the sidebar (or deletes the active one). `activeSessionId` changes, the `loadMessages` effect (`ChatContext.jsx:87-120`) replaces `messages` with the newly-selected session's history, and then the still-running stream's next `token`/`completion` event appends/overwrites into that unrelated session's message array.
2. **Auth tokens stored in `localStorage` by default** — `frontend/src/api/supabaseClient.js:8` (`createClient(supabaseUrl, supabaseAnonKey)` with no `auth: { storage: ... }` override). Supabase's default persists the access/refresh token pair in `localStorage`, which any injected script (XSS in this app or in a transitive dependency) can read directly — unlike an httpOnly cookie. This is a default, not a deliberate choice, and it's worth deciding explicitly given the app also handles document uploads and chat content from external sources.
3. **Advertised upload size limit doesn't match what's enforced, and neither is checked client-side** — `frontend/src/components/Upload/UploadButton.jsx:129` (UI text: "Max 15MB") vs `backend/app/config/settings.py:14` (`MAX_UPLOAD_SIZE_MB: int = 10`, the actual server-enforced limit). Neither `isValidFile` (`UploadButton.jsx:17-22`) nor `useUpload.js:10-33` check file size before starting the upload. *Failure scenario:* a user selects a 12MB file — under the UI's advertised 15MB, so nothing warns them — the entire file uploads over the network (with progress UI implying success), and only then does the backend reject it with a 413, wasting the user's upload time/bandwidth for a limit the UI told them didn't apply.
4. **Unbounded base64 images retained in React state indefinitely** — `frontend/src/components/Chat/ChatInput.jsx:22-36` (`handleImageSelect` calls `reader.readAsDataURL(file)` with no size check) and the resulting data URI is stored as `image_data` directly in the message object (`ChatContext.jsx:168`) and kept in the `messages` array for the lifetime of the session. *Failure scenario:* a user attaches several multi-MB images across a long conversation; every one of them stays fully materialized as a base64 string in memory (and gets included whenever `messages` is copied/spread on every subsequent state update), which will visibly slow down or crash the tab on lower-end devices.
5. **`localStorage.clear()` on logout wipes unrelated app data** — `frontend/src/context/AuthContext.jsx:54`. *Failure scenario:* any other same-origin data the app or a future feature stores in `localStorage` (a draft message, a UI preference, an unrelated flag) is silently deleted on every logout, not just the auth session.
6. **Deferred session-clear on logout can race a fast re-login** — `frontend/src/context/ChatContext.jsx:47-53`: the state reset when `user` becomes falsy is wrapped in `setTimeout(..., 0)` rather than running synchronously. *Failure scenario:* a user logs out and immediately logs back in (or switches accounts) fast enough that the new user's session data loads before the deferred clear fires; the clear then wipes state that belongs to the new user, briefly blanking the UI.
7. **No memoization during token streaming** — `frontend/src/components/Chat/MessageList.jsx` and `MessageItem.jsx` have no `React.memo`/list virtualization. Every SSE token event replaces the entire `messages` array (`ChatContext.jsx:194-207`), which re-renders every `MessageItem` in the conversation, not just the streaming one. *Failure scenario:* on a long chat history, each of the (potentially hundreds of) tokens streamed in a single response triggers a full list re-render, producing visible jank proportional to conversation length.
8. **Minor:** `SourceBadge.jsx:14` uses the array index as the React `key` instead of a stable identifier (harmless today since the sources array for a given message never reorders in place, but a latent footgun if it ever does); `ChatContext.jsx:22-42` (`fetchSessions`) duplicates logic already inline in the `user`-effect (`ChatContext.jsx:56-78`) almost verbatim — not dead code (it's exposed via context and could be called to refresh the list), but the two copies will drift if one is changed without the other.

**Verified working correctly, no issue found:** no XSS in message rendering — `MessageItem.jsx:45` renders `message.content` inside a plain `<div>` (React's default escaping applies), no `dangerouslySetInnerHTML` anywhere in the component tree; `ProtectedRoute.jsx:8-10` correctly blocks on `loading` before evaluating `isAuthenticated`, so there's no flash of protected content; `streamParser.js`'s SSE buffering correctly holds back an incomplete trailing line (`buffer = lines.pop() || ""`) and flushes it at stream end, with no unbounded buffer growth; `axios.js`'s request interceptor (`:12-22`) re-fetches the Supabase session token on every request rather than caching a stale one.

## Test suite (`backend/tests/`)

Ran `pytest --collect-only`; 15 tests collected across 9 files (`test_model.py` and `test_contextualize.py`/`fix_db.py`-style scripts contribute no collected tests — they have no `test_`-prefixed functions).

- **The reflection loop's max-retry cap has no test coverage at the graph level.** `tests/test_reflection.py::test_reflection_retry` calls `evaluate_response()` and `run_answer_agent()` directly as plain functions; it never invokes `rag_graph` or `graph.py`'s `route_after_reflection`, so the actual loop-termination logic (`retry_count < max_retries` at `graph.py:80`, the `"supervisor"` re-entry edge) is never exercised end-to-end. A regression that turned this into a genuine infinite loop (e.g. someone "fixing" the retry-count increment logic in `answer_node` and accidentally decoupling it from `route_after_reflection`'s check) would not be caught by any existing test.
- **The web-search-fallback-skips-reflection behavior (Fix First #3) has no test coverage.** No test asserts on `route_after_vector_search` → `web_search_node` → `route_after_answer`'s interaction, or checks that `tool_outputs` does/doesn't contain a `"reflection"` entry for that path.
- **IDOR coverage is partial.** `tests/test_security.py::test_idor_security` covers `POST /search` and `POST /chat` for cross-user access, but there is no equivalent test for `GET /sessions/{id}`, `GET /sessions/{id}/messages`, `PATCH /sessions/{id}`, `DELETE /sessions/{id}`, or `POST /upload` — all of which independently implement the same ownership check in `crud.py`/`upload.py` and could regress independently of the tested paths.
- **Two "tests" always report PASSED regardless of whether the thing they test actually works**, because `pytest.ini` sets `asyncio_mode = auto`, so both are collected and run as real async tests despite being written as manual diagnostic scripts:
  - `tests/test_db.py::test_connection` wraps its entire body in `try/except Exception as e: print(...)` (`test_db.py:9-40`) and never calls `assert` or `pytest.fail()`. A broken `DATABASE_URL`, a missing `pgvector` extension, or a failed `Base.metadata.create_all()` all just print an error and the test still shows green.
  - `tests/test_gemini.py::test_gemini_connection` does the same (`test_gemini.py:18-29`) and additionally makes a real, unmocked network call to the live Gemini API with the configured `GEMINI_API_KEY` on every `pytest` invocation — burning real API quota for a test that can never actually fail.
- **No test covers the chunk-overlap bug (Fix First #2) at all** — there is no `test_chunking.py`; had one existed asserting that consecutive chunks share overlapping text, it would have caught this immediately.

## Verified working correctly / no issue found (additional, not covered above)

- `web_search_tool` (`backend/ai/tools/web_search.py:29-80`) correctly offloads the blocking DuckDuckGo call via `asyncio.to_thread` (line 36) and has no SSRF surface — the search query is user text, not an attacker-controlled URL.
- The reflection retry loop's cap logic itself (as written) is sound: `answer_node` (`graph.py:147-155`) increments `retry_count` only when the incoming state already carries an `error`, and `route_after_reflection` (`graph.py:71-87`) stops routing back to `"supervisor"` once `retry_count >= 2`. Tracing it by hand for a persistently-failing reflection: attempt 1 → `retry_count=0`, attempt 2 → `retry_count=1`, attempt 3 → `retry_count=2` → loop terminates. (Flagged above only for lacking automated test coverage, not for being wrong.)
- Alembic's revision chain is linear and consistent (`alembic heads` → single head `f06fbea045e1`), so there's no branching/merge-conflict risk in the migration history itself — the problem is purely that the migrations don't create what their names promise.
